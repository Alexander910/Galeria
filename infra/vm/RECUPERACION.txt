ESTADO Y DIAGNÓSTICO
Desde el equipo con Azure CLI:
  az vm list -g nogal-final -d -o table
  az deployment group show -g nogal-final -n nogal-final-v3 --query properties.provisioningState
Desde cada VM de aplicación mediante RunShellScript:
  systemctl status nogal --no-pager
  journalctl -u nogal -n 60 --no-pager
  docker logs --tail 60 nogal
No ejecutar cat /etc/nogal/app.env ni comandos de tokens al preparar evidencias.
GET /api/health devuelve el nombre de la réplica. Es un sondeo de proceso HTTP;
no prueba por sí solo que Vision, Blob y Tables estén disponibles.

FALLA DE UNA RÉPLICA
1. Comprobar que el otro nodo responde a través de ambos accesos públicos.
2. Consultar el log del nodo afectado. El servicio systemd reinicia Docker automáticamente.
3. Recuperar un nodo sin detener el otro:
  az vm run-command invoke -g nogal-final -n nogal-app-1 --command-id RunShellScript --scripts "systemctl restart nogal; systemctl is-active nogal"
4. Repetir GET /api/health y /api/session y comprobar app1 y app2. Esperar los dos
   sondeos correctos de HAProxy (intervalo 3 s, rise 2). Las sesiones están en Tables.
5. Si la VM se perdió, reutilizar infra/vm/main.bicep y server.bicep. Generar el paquete
   con build-package.py y compilar con Bicep. Los parámetros privados permanecen en
   data/deploy, fuera del paquete académico. Revisar what-if antes de redesplegar.
6. En una actualización cambiar un nodo, comprobar salud y después cambiar el otro.
   No reiniciar ambos simultáneamente durante una demostración.

FALLA DEL BALANCEADOR
1. Abrir el acceso alternativo. Este cambio de URL es manual; no hay DNS con failover.
2. En la VM proxy afectada:
  haproxy -c -f /etc/haproxy/haproxy.cfg
  caddy validate --config /etc/caddy/Caddyfile
  systemctl restart haproxy caddy
  curl -fsS 'http://127.0.0.1:8404/stats?stats;csv'
3. Revisar journalctl -u haproxy y journalctl -u caddy. No exportar secretos ni cookies.
4. proxy-init.sh es la fuente de configuración. Reemplazar __PUBLIC_HOST__ por el FQDN
   del proxy correspondiente. El segundo proxy usa Belgium Central y el primero North
   Central US. Ambos consumen las mismas dos aplicaciones privadas.
5. Una caída de toda la región primaria también afecta aplicaciones y base. El proxy
   secundario por sí solo no resuelve ese escenario; no anunciar recuperación regional.

BASE DE DATOS Y CONECTIVIDAD
La cuenta nogaldbuietolmehuftu tiene publicNetworkAccess=Disabled y Shared Key=false.
Tablas: users, sessions, artworks. Cada entidad usa PartitionKey=kind, RowKey=id y payload
JSON. La cuenta usa LRS; no hay réplica de datos en otra región ni point-in-time restore.
Si hay timeout, revisar antes de restaurar: endpoint privado nogal-database-private,
zona privatelink.table.core.windows.net, vínculos a ambas VNet y emparejamiento global.
En app u ops:
  getent hosts nogaldbuietolmehuftu.table.core.windows.net
El resultado debe resolver a la dirección privada del endpoint.
Ante 403, revisar RBAC y la identidad asignada, sin habilitar claves compartidas ni
acceso público. Los roles pueden tardar unos minutos en propagarse.

RECUPERAR REGISTROS O IMÁGENES
1. Elegir un respaldo y guardar otro del estado actual. Si cambia la base, poner ambas
   aplicaciones en mantenimiento (systemctl stop nogal) para evitar escrituras concurrentes.
2. La identidad de ops puede leer respaldo y fuentes pero NO escribir en users/artworks.
   La restauración debe ejecutarla una identidad autorizada de aplicación, en su VNet.
3. Desde Azure CLI, conceder temporalmente a nogal-app-identity el rol Storage Blob Data
   Reader SOLO en el contenedor backups. Obtener principalId de az identity show y el
   scope de az storage account show (id + /blobServices/default/containers/backups).
   Registrar el ID de la asignación para retirarla al terminar. No otorgar Owner a la VM.
4. Usar prepare-restore-check.py para preparar el script de descarga y verificación.
   Cambiar el nombre del respaldo por el elegido. Ejecutar el script mediante RunCommand
   en nogal-app-1; crea un directorio local privado y extrae el tar.gz dentro de un
   contenedor sin privilegios. El último comando es una simulación:
  docker run --rm -v /var/lib/nogal-backup/recovery-check:/restore:ro -v /opt/nogal/restore.cjs:/app/restore.cjs:ro nogal:project node restore.cjs /restore
5. Revisar conteos y tamaños. Para aplicar, usar el mismo montaje, añadir
   --env-file /etc/nogal/app.env después de --rm, y --apply después de /restore.
   restore.cjs sube archivos y repone entidades por ID; NO borra obras nuevas que no
   estén en el respaldo. Invalida todas las sesiones. Una recuperación total requiere
   resolver explícitamente los registros sobrantes, no borrarlos por suposición.
6. Reiniciar app1 y app2, verificar login, historial, archivos y etiquetas. Retirar la
   asignación temporal de lectura de backups. Limpiar los archivos temporales privados.
7. Objetivo de pérdida de datos: hasta 24 horas con timer diario si los respaldos pasan.
   No se midió RTO completo; no prometer un tiempo de restauración no probado.

APROVISIONAMIENTO
build-package.py genera data/deploy/nogal-source.tar.gz y app-init.sh. main.bicep consume
ese script, usa identidades administradas, Key Vault y parámetros seguros. Compilar:
  bicep build infra/vm/main.bicep --outfile data/deploy/nogal-five-servers.json
Desplegar usando el archivo privado local de parámetros. Una instalación en otra cuenta
requiere tres hashes scrypt/salt, una clave SSH pública, cuotas y regiones permitidas.
No distribuir data/deploy/nogal-five-servers.parameters.json, nogal-admin, users.json,
tokens de .tools, archivos .env ni archivos de respaldo. El JSON ARM del paquete no
contiene valores de contraseña; solicita bootstrapUsers como secureString.
